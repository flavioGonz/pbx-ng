# Changelog

Formato basado en [Keep a Changelog](https://keepachangelog.com). Versionado: [SemVer](https://semver.org).

## [1.5.1] - 2026-09-05
### Fixed
- La API salía con código 1 en cada arranque hasta que Asterisk levantaba: `ari-client` no rechaza la promesa cuando ARI no escucha sino que tira la excepción en un callback suelto, y el manejador de `uncaughtException` de 1.5.0 la tomaba como fatal. Ahora se sondea el HTTP de ARI (`/ari/api-docs/resources.json`) antes de conectar y se reintenta con el backoff de siempre.

## [1.5.0] - 2026-09-05
Sprint 2 de robustez: cierra los **bloques 2 y 3** de `docs/EVALUACION-2026-09.md` (que el release no pierda datos; que el proceso no muera solo). Sin cambios de esquema visibles para el operador: la migración `0009` sólo formaliza tablas que antes creaba el código al vuelo. Tres cosas que conviene leer antes de actualizar: las **migraciones corren solas al arrancar la API** (y si fallan, la API no arranca), **`/health` responde 503 sin base de datos** (los monitores externos van a verlo) y el **socket.io rechaza orígenes ajenos** (en desarrollo, `CORS_ORIGINS`).
### Added
- **Respaldo programado**, con dos caminos equivalentes que hacen exactamente lo mismo (`backup.programado()` = crear + retención):
  - *Planificador interno de la API*, configurable desde **Sistema → Respaldos → «Respaldo programado»** (`GET/POST /api/backup/schedule`, sólo admin): interruptor, hora (0–23, reloj local del contenedor) y cuántos conservar. **Viene activo por defecto a las 03:00** en toda instalación, aunque nadie instale un cron. Revisa cada minuto y no repite el respaldo de hoy si ya hay uno (marca `backup_last_run` en `pbxng_settings`). El panel muestra la última corrida (fecha, correcta/falló) y dice «No disponible en esta versión» si la API es más vieja.
  - *Cron del host* (opcional): `install.sh` instala `0 3 * * * /opt/pbx-ng/docker/backup-cron.sh` en `/etc/cron.d/pbxng-backup` (o en el crontab del usuario), idempotente; el script entra por `docker compose exec` a la API y corre el nuevo `control-plane/backup-cli.js` (`--keep=N --grabaciones --nota= --list`), con `flock` para no solapar y log en `/var/log/pbxng-backup.log` (se recorta solo al pasar 1 MB). A mano: `pbxng-ctl backup [args]`.
  - Los respaldos automáticos se llaman `pbxng-auto-AAAAMMDD-HHMM.tar.gz` y llevan `programado:true` en el manifiesto (`GET /api/backup` lo devuelve por ítem). **La retención (`BACKUP_KEEP`, default 14) borra sólo los `pbxng-auto-*` que sobran; los respaldos hechos a mano desde el panel no se tocan nunca.** Si la creación falla no se poda nada.
- **Healthcheck en los 8 servicios** del compose, con la herramienta que cada imagen trae de verdad: postgres `pg_isready`, asterisk `core show uptime` por la CLI (el PID vivo no alcanza: Asterisk puede colgarse), api `GET /health/ready`, dashboard `GET /login` con el propio Node, coturn TCP 3478 (python3), voz `GET /health` (start_period 120 s por la carga de modelos), go2rtc `GET /api` (wget), npm `:81`. `docker compose ps` y `pbxng-ctl status` muestran `healthy`/`unhealthy` reales.
- **Límites de memoria por contenedor** (`mem_limit` = `memswap_limit`, o sea sin swap: Asterisk paginando corta el audio, mejor que Docker lo reinicie limpio). Variables `MEM_POSTGRES MEM_ASTERISK MEM_API MEM_DASHBOARD MEM_COTURN MEM_VOZ MEM_GO2RTC MEM_NPM` en `.env` (defaults `1g 1g 768m 512m 256m 4g 512m 512m`).
- **Rotación de logs** de Docker: `json-file` 10 MB × 5 por contenedor (`x-logging` en ambos compose).
- **Drenado de Asterisk antes de recrearlo** (`docker/asterisk-drain.sh`): cuenta las llamadas activas, pide confirmación si hay (salvo `--yes`; sin terminal aborta), manda `core stop gracefully` (no acepta llamadas nuevas y espera a que cuelguen las activas), espera hasta `--timeout` (60 s) y para el contenedor. `pbxng-ctl up|enable|down|reconcile` y `deploy.sh` lo llaman **sólo si el `up -d` va a recrear asterisk** (según `docker compose --dry-run`; `reconcile` corre desde el timer sin terminal y drena sin preguntar). Nuevos `pbxng-ctl drain` y flag global `--yes`. `stop_grace_period`: asterisk 60 s, api 20 s.
- **Cierre ordenado de la API** ante `SIGTERM`/`SIGINT` (`docker stop`, `compose down`, `up -d` que recrea): deja de aceptar conexiones, cierra socket.io, corta las supervisiones activas (snoop), cierra ARI/AMI y el AudioSocket, espera hasta 10 s a que terminen las consultas y sale con 0; a los 15 s sale con 1. Cada paso queda en el log (`cierre: …`). `unhandledRejection` se loguea sin tumbar el proceso; `uncaughtException` loguea y sale con 1.
- **Logger con niveles y JSON** (`control-plane/log.js`, sin dependencias): cada línea es `{ts, level, mod, msg, …}`; los `Error` salen con `message`/`code`/`stack`; `warn`/`error` a stderr. `LOG_LEVEL` (`debug|info|warn|error`, default `info`) y `LOG_FORMAT=text` para leer a mano en desarrollo. Reemplaza los 55 `console.*` de `app.js` y los de `ai-pipeline`, `push-providers`, `callengine`, `sipconf`, `alerts`, `recstore`, `migrate`; el prefijo viejo (`[ARI]`, `[PUSH]`…) es ahora el campo `mod`.
- **Middleware de error** (`control-plane/errores.js`): `errorHttp(res, e)` en los `catch` de las rutas (224 reemplazos) respeta `e.status` con mensaje propio y **traduce los errores de PostgreSQL** a un mensaje genérico en español con status por clase (`23505` → 409 «ya existe un registro con ese valor», `23503` → 409, `23502`/`22xxx` → 400, `57014` statement_timeout → 504, conexión caída → 503 «sin conexión con la base de datos…», resto → 500 «error interno de la base de datos»); el detalle real (código, tabla, constraint, stack, método y ruta) va al log. Manejador final de Express: `500 {error:'error interno'}` siempre (los `throw` con `e.status` 4xx conservan su mensaje). Ruta inexistente bajo `/api` con sesión → `404 {error:'ruta inexistente'}`.
- **`GET /health` y `GET /health/ready`** (idénticos): `200 {status:'ok', db:true, db_ms, ari, ami, shutting_down:false, ts}` si la base contesta en 2 s (aunque ARI/AMI estén caídos, se reportan); `503 {status:'degraded', db:false}` si no; `503 {status:'shutting_down', db:<lo medido>}` durante el cierre. El `HEALTHCHECK` del Dockerfile y el del compose apuntan a `/health/ready`.
- **Pool de PostgreSQL acotado**: `PG_POOL_MAX` (default 10), `idleTimeoutMillis` 30 s, `connectionTimeoutMillis` 5 s, `PG_STATEMENT_TIMEOUT_MS` (default 30000; Postgres cancela lo que pase de ahí → 504 en la ruta) y `query_timeout` = +5 s del lado del cliente.
- **Panel: estado degradado visible.** Banner rojo «Base de datos sin respuesta — La central sigue atendiendo llamadas pero el panel no puede guardar cambios» arriba del contenido del shell cuando el `snapshot` del socket trae `health.db=false`; con el socket caído consulta `GET /backend/health` cada 30 s (y deja de hacerlo apenas el socket vuelve). Si la API no contesta en absoluto no inventa «base caída»: eso ya lo dice el indicador Offline.
- **Panel: barrera de errores.** `app/ErrorBoundary.jsx` envuelve sólo el contenido de cada pantalla: si una página revienta aparece «Algo se rompió en esta pantalla» con el mensaje, botones Reintentar / Recargar, y el menú sigue usable; se resetea sola al cambiar de ruta. `app/error.jsx` y `app/loading.jsx` del App Router, en español.
- Docs: `docs/CONTRATOS.md` §3 (errores, health, cierre, logs, `backup/schedule`), §4 (origen del socket), §6 (variables nuevas), §7 (healthchecks, límites, drenado, respaldo programado), §9 (migraciones al arrancar); `docker/README.md` («Operación», «Robustez del stack», «Respaldo programado»); `docs/PACKAGING.md`; manual in-panel de configuración (Respaldos y estado degradado); `docs/EVALUACION-2026-09.md` (bloques 2 y 3 marcados ✅ 1.5.0).
### Changed
- **BREAKING — el esquema lo crean las migraciones, al arrancar.** `control-plane/docker-entrypoint.sh` espera a Postgres (60 s; si no aparece sale con 1, antes «arrancaba igual»), corre `node migrate.js` y recién después `exec node app.js`. **Si una migración falla, el contenedor de la API sale con 1 y no arranca con esquema viejo** (antes seguía andando). Nueva `migrations/0009_schema_runtime.sql` con los mismos `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` que hasta ahora ejecutaban `app.js`, `ai-pipeline.js` y `push-providers.js` en tiempo de ejecución (`pbxng_settings`, `push_subs`, `push_devices`, `users.ext/must_change`, `enroll` + 6 columnas, `fail2ban*`, `recordings` + 4 columnas, `rec_config` + `nas_*`, `prompts`, `email_config`, `integrations`, `ai_agents` + 5 columnas, `ivr.flow`, `trunks.kind/kam_config`, `outbound_routes`, `ivr_audios`, `inbound_routes`, `directory`, `click2call`, `c2c_sessions`, `phones`, `call_geo`, `captures`, `net`, `moh_classes`, `sip_capture`, `clients` + `lat/lon`, `client_persons/spaces/devices`, `survey_fields`, `call_surveys`): **ningún módulo crea tablas ni columnas en runtime**; quedan sólo filas semilla idempotentes. En una instalación existente 0009 no hace nada (todo ya existe); en una nueva, `initdb/01-schema.sql` trae casi todo y 0009 completa `pbxng_net` y `pbxng_moh_classes`. `migrate.js` toma `pg_advisory_lock` (dos réplicas no migran a la vez), protege el `ROLLBACK` y sale con 1 y mensaje claro (host:puerto) si no conecta. Instalación sin Docker (`infra/systemd/pbxng-api.service`): hay que correr `node migrate.js` antes de `node app.js` (hoy no rompe porque las tablas ya existen).
- **BREAKING — `/health` responde 503 sin base de datos** (antes siempre 200). Un monitor externo que lo mire va a alertar cuando Postgres no contesta, que es lo que corresponde. Con la base bien, sigue en 200 aunque ARI/AMI estén caídos.
- **BREAKING — límites de memoria.** Un contenedor que pase su `MEM_*` es reiniciado por Docker (`OOMKilled` en `docker inspect`). Los defaults cubren el uso normal; si voz usa un modelo whisper grande o Asterisk graba muchas llamadas a la vez, subir `MEM_VOZ` / `MEM_ASTERISK` en `.env` y `pbxng-ctl up`.
- **BREAKING — socket.io ya no acepta cualquier origen** (`cors.origin` dejaba de ser `'*'`): se acepta un handshake **sin** `Origin` (proxy del panel, curl, softphone nativo), uno cuyo `Origin` coincide con el `Host`/`X-Forwarded-Host` con el que llegó, o uno listado en `CORS_ORIGINS` (coma). El resto: `403 {code:4, message:'origen no permitido'}` y log `mod: SOCKET`. Vía el proxy del panel (`dashboard/server.js`) no cambia nada; en `npm run dev` con el panel en `:3001` pegándole directo a `:3000` hay que poner `CORS_ORIGINS=http://localhost:3001`. Detrás de NPM en un puerto no estándar (p. ej. `https://pbx:8443`) el `Origin` trae el puerto y el `Host` no: agregar ese origen a `CORS_ORIGINS`.
- `deploy.sh` corre las migraciones antes del `up -d` con `run --rm --no-deps --entrypoint node api migrate.js` (el entrypoint de la imagen ignora los argumentos y habría dejado la API entera en primer plano, colgando el deploy) y **aborta con exit 1 si fallan** (antes seguía con un `echo`), para que un esquema roto frene el deploy con el error a la vista en vez de dejar la API en crash-loop. Acepta `--yes`.
- `pbxng-ctl` honra `PBXNG_COMPOSE_FILE` del `.env` (antes usaba siempre `docker-compose.yml` aunque la instalación fuera `--release`); `install.sh` lo escribe en ambos roles junto con `BACKUP_KEEP=14` si falta.
- `release.sh`: el bundle air-gapped incluye `asterisk-drain.sh`, `backup-cron.sh`, `check-compose-parity.sh` y los tres archivos del reconciliador (faltaban y `pbxng-ctl` los necesita).
- `docker-compose.release.yml` regenerado desde el canónico (paridad verificada por `check-compose-parity.sh`). `.env.example`: secciones `MEM_*`, `BACKUP_KEEP`, `PBXNG_COMPOSE_FILE`.
- Panel: `GET /api/backup` trae `programado` por respaldo; la pantalla `/respaldos` suma la tarjeta «Respaldo programado» entre «Crear un respaldo nuevo» y la lista.
### Fixed
- **AudioSocket duplicado** (`ai-pipeline.js`): `init()` se llamaba en cada reconexión de ARI y volvía a hacer `listen` en `:9092` → `EADDRINUSE`. Ahora el servidor es único, con manejador de `error`, y `close()` lo cierra en el apagado ordenado.
- Rutas que devolvían texto crudo de PostgreSQL (`relation "x" does not exist`, `connect ECONNREFUSED 127.0.0.1:5432`) al panel: ahora mensaje genérico en español y el detalle en el log (ver `errores.js`).
- `GET /api/sip/messages` creaba la tabla `pbxng_sip_capture` en cada pedido; vive en 0009.
- `docker-entrypoint.sh` con Postgres ausente: sale con 1 y mensaje (antes arrancaba la API contra nada y llenaba el log de `ECONNREFUSED`).

## [1.4.0] - 2026-09-05
Sprint 1 de seguridad: cierra el **bloque 1** de `docs/EVALUACION-2026-09.md` (control de acceso) y parte del bloque 2 (paridad del release, Redis, puertos). El contrato entre componentes vive en `docs/CONTRATOS.md`.
### Added
- **Configuración → SIP** (sólo admin), al estilo de las centrales de marca: pestañas General (User-Agent, keep-alive, Max-Forwards, realm, Timer T1/B), NAT (IP externa de señalización y medios, redes locales, ToS SIP), RTP / ToS (rango RTP, strictrtp, ICE, STUN, timeout DTMF, ToS de audio), Session Timer (RFC 4028, con «aplicar a todos»), TCP / TLS (versión y cifrados, transportes activos) y Códecs por defecto para internos/troncales nuevos. Backend nuevo `control-plane/sipconf.js`: guarda en `pbxng_settings.sipconf`, genera `pbxng.d/pjsip.conf` y `pbxng.d/rtp.conf` (secciones `(+)` incluidas desde los `.conf` base de la imagen de Asterisk), recarga `res_pjsip`/`res_rtp_asterisk` y avisa cuando el cambio (NAT, TLS, rango RTP) sólo entra con reinicio, ofreciendo `core restart when convenient`. Rutas `GET/POST /api/sipconf`, `POST /api/sipconf/restart`. Los endpoints nuevos heredan temporizadores, ToS y códecs por defecto.
- **La grabación global de llamadas** se movió de `/internos` a Configuración → SIP (el editor del interno sigue avisando cuando está activa).
### Fixed
- **Notificaciones (toasts)**: el fondo tomaba el color del estado (verde/rojo) y sileo pinta el título con ese mismo color, así que el texto se fundía con el fondo; ahora el fondo sigue al tema del panel y el color queda en título, icono y barra. Se quitó el `text-transform: capitalize` (rompía direcciones de correo) y se agregaron las animaciones SVG de los iconos por tipo (trazo que se dibuja, halo, auricular que vibra, onda de audio, spinner), cuyas clases estaban referenciadas pero nunca definidas.
### Security
- **Control de acceso por rol (RBAC) en toda `/api`.** Nuevo `control-plane/rbac.js`: una tabla única (método + ruta → roles), *deny-by-default*, montada en `/api` justo después del gate de auth y **antes de cualquier ruta** (incluidas las de `callengine.js`, que antes quedaban fuera del gate). Lo que no figura en la tabla es sólo `admin`. Rechazo: `403 {error:'no tenés permiso para esta acción'}`. Resumen por rol en `docs/CONTRATOS.md` §2. **BREAKING:** los roles son exactamente `admin`, `supervisor` y `agente`; los viejos `operator`/`viewer` se convierten solos (`operator` → `supervisor`, `viewer` → `agente`) por la migración `0008_roles.sql` y por el bootstrap de la API al arrancar, y un usuario con cualquier otro rol recibe `403` con mensaje claro en el login (no se emite JWT).
- **«Sobre su extensión» de verdad.** `extPropia()`/`exigirExt()`/`mismaExt()`: un agente (o un token de softphone) sólo opera su interno en `calls/dial|transfer|park|record|conference`, `push/test`, `vm*`; `GET /api/cdr` le fuerza su extensión; `recordings/match` y `recordings/:id/audio` sólo devuelven llamadas en las que participó.
- **Usuarios (`/api/users`, sólo admin).** **BREAKING:** el rol por defecto al crear pasa de `admin` a `agente`; `role` se valida contra la lista; contraseñas de 8+ caracteres (alta y `users/:id/password`, que ahora devuelve 404 si el id no existe); no se puede borrar el propio usuario ni el último administrador.
- **Cambio de clave propia (`POST /api/auth/password`)** exige la contraseña actual (`current`, `403` si no coincide) salvo en el primer ingreso (`must_change`); mínimo 8 caracteres.
- **Enlace/QR de enrolamiento (`GET /api/enroll/:token`).** **BREAKING:** de un solo uso (`used_at`) con ventana de gracia `ENROLL_REUSE_SECONDS` (default 120 s) para que la PWA y el softphone del mismo aparato lo canjeen seguido; después responde `410 {error:'token ya usado'}`. El `apiToken` que entrega (y el de `GET /api/provision`) es ahora un **token de alcance `phone`** (30 d), nunca una sesión de panel: el QR de un interno de admin ya no vale como sesión de administrador por un mes. Para el CRM completo, intercom, grabaciones o supervisión el softphone necesita iniciar sesión con usuario y contraseña.
- **Token de softphone (`FONO_PERMITIDO`)**: `push/*` se reduce a `POST push/subscribe|register|unsubscribe|test` (el comodín dejaba leer `GET push/devices`, inventario de todas las extensiones, ahora sólo admin) y se abren `GET /api/cdr` (forzado a su ext) y `GET /api/clients/lookup` para que el softphone conserve historial propio y screen-pop.
- **Login y `POST /api/phone/token` con rate limit** (`express-rate-limit`): 10 fallos / 10 min por IP+usuario (o IP+ext) **más** 50 fallos / 10 min por IP sola (contra *password spraying*); sólo cuentan los fallos; `429 {error:'Demasiados intentos. Esperá 10 minutos y volvé a probar.'}`. Reemplaza el contador artesanal `FONO_INTENTOS`. La IP es siempre `req.ip` con `trust proxy = 1` (antes se leía el primer valor de `X-Forwarded-For`, que escribe el propio cliente: rotarlo salteaba cualquier límite y falseaba la IP de la bitácora y del enrolado). `bcrypt` asíncrono en login, cambios de clave y bootstrap del admin (el `compareSync` bloqueaba el event loop ~100 ms por intento).
- **`helmet`** (CSP apagada, `Cross-Origin-Resource-Policy: cross-origin`) en la API: `nosniff`, `X-Frame-Options`, `Referrer-Policy`, sin `X-Powered-By`.
- **La API no arranca sin `JWT_SECRET` real**: vacío, placeholder `__SET_JWT_SECRET__` o de menos de 16 caracteres → mensaje claro y `exit 1` (antes seguía andando con el placeholder y cualquiera podía firmarse una sesión de admin).
- **socket.io exige JWT en el handshake.** **BREAKING:** `auth.token` (sesión de panel) o `auth.scratch` (token de softphone, scope `phone`); `scratch: true` a secas ya no conecta (cualquiera podía sumarse a la pizarra de una videollamada ajena). Un token `phone` queda limitado a la pizarra: no entra a la sala `state` ni recibe `snapshot`.
- **Panel: proxy propio hacia la API (`dashboard/server.js`).** Reemplaza los `rewrites` de Next (que no agregaban `X-Forwarded-For`, así que por `:3001` todos compartían la IP del contenedor y un XFF inventado pasaba intacto). Reenvía `/backend/*`, `/socket.io` (HTTP y upgrade WebSocket), `/prov/*` y `/descargas/softphone/*` dejando la IP real del cliente como último elemento de `X-Forwarded-For`; `TRUST_PROXY` (o el perfil `proxy` en `COMPOSE_PROFILES`) dice cuántos saltos confiar. Con la API caída responde `502 {error}` en vez de una página rota. `useLive.js` conecta el socket siempre al mismo origen (antes saltaba directo a `:3000` cuando el panel corría en `:3001`).
- **Puertos.** **BREAKING:** `5432` (Postgres) y `3000` (API) ya no se publican en `0.0.0.0` en ningún compose: quedan en `127.0.0.1` del host, sólo porque Asterisk (host network) necesita la base y `/api/internal/wake`. Para usar la DB desde otra máquina: túnel ssh. `DB_HOST` pasa a `127.0.0.1` (sólo lo usa Asterisk; la API va por la red interna). El panel se publica en `${DASHBOARD_BIND:-0.0.0.0}:3001`: con el perfil `proxy` en el mismo compose `install.sh`/`pbxng-proxmox.sh` lo atan a `127.0.0.1` (se entra por 443 vía NPM); con el proxy en otro host/CT va `0.0.0.0` + `DASHBOARD_TRUST_PROXY=1` y hay que restringir `:3001` a la IP del proxy por firewall. `TURN_PASS`/`TURN_CLI_PASS` ya no tienen default en ningún compose (`${VAR:?}`).

- Dependencias nuevas en `control-plane`: `helmet` 8.3, `express-rate-limit` 8.7 (lockfile regenerado).
